# Проходные — мониторинг турникетов

Сервис для PERCo KT02.9 (контроллер CT13.1): слушает журналы нескольких
турникетов, складывает передвижения в SQLite и показывает их на веб-интерфейсе
в реальном времени. Проходные добавляются в интерфейсе по адресу и названию
(алиасу), в дашборде есть фильтр по проходной.

![status](https://img.shields.io/badge/read--only-yes-brightgreen)

## Что делает

- Держит по одному WebSocket-соединению `ws://<ip>/tcp` на каждую проходную.
- Использует штатный протокол веб-интерфейса PERCo: JSON поверх WebSocket.
- Отправляет **только запросы на чтение** (`get: sysinfo`, `get: event`,
  `get: event_count`). Настройки контроллеров не изменяются.
- Раз в `POLL_INTERVAL` секунд забирает новые события каждого журнала и
  сохраняет их в SQLite.
- По умолчанию собирает только категорию `0` — «Доступ по идентификатору»
  (успешные проходы и отказы по предъявленным картам).
- Отдаёт данные фронтенду через REST API и SSE-поток (`/api/stream`).
- При первом запуске каждой проходной импортирует историю за `BACKFILL_DAYS`
  дней (`0` — всю историю).

Сохраняются события доступа по идентификатору — и успешные проходы, и отказы по
неизвестным или невалидным картам. В интерфейсе по умолчанию показаны все они;
галочка «Только проходы» оставляет только успешные. Для каждого события доступны
**код карты** (`card`), **UID** (`uid`), направление (вход/выход), тип
идентификатора и тип пользователя.

## Требования

- Docker 24+ и Docker Compose v2 — для запуска в контейнере.
- Сетевая доступность веб-интерфейса турникета (порт 80 по умолчанию).
- Свободный порт `8080` на машине, где запускается сервис.
- Для запуска без Docker: Python 3.11+.

## Быстрый старт (Docker)

### 1. Подготовьте `.env`

```bash
cp .env.example .env
```

Минимально нужно указать адрес первой проходной:

```env
TURNSTILE_HOST=192.168.1.100
TURNSTILE_NAME=КПП-1
TURNSTILE_PORT=80
TURNSTILE_PASSWORD=
```

`TURNSTILE_HOST` используется **только один раз** — для создания первой
проходной на пустой базе. Дальше устройства добавляются в интерфейсе.

### 2. Запустите

```bash
docker compose up -d --build
```

### 3. Проверьте

```bash
docker compose ps
# STATUS должен быть healthy

curl -s http://localhost:8080/api/health
# {"ok":true}

curl -s http://localhost:8080/api/devices
```

Откройте <http://localhost:8080>. В шапке появится статус связи; если турникет
доступен — «1 из 1 на связи».

### 4. Добавьте остальные проходные

В интерфейсе — кнопка **«Проходная»**: название (алиас), адрес, порт, пароль
(если задан на контроллере). Или через API:

```bash
curl -X POST http://localhost:8080/api/devices \
  -H 'Content-Type: application/json' \
  -d '{"name":"КПП-2","host":"192.168.1.101","port":80}'
```

Адрес можно передавать как `192.168.1.101`, `192.168.1.101:8080` или
`http://192.168.1.101/` — схема, путь и порт разбираются автоматически.

## Режимы запуска

### Linux / общая сеть

Если машина с Docker находится в той же сети, что и турникеты, ничего
дополнительно настраивать не нужно. Оставьте relay-переменные пустыми:

```env
TURNSTILE_RELAY_ENDPOINT=
TURNSTILE_RELAY_TOKEN=
RELAY_ALLOWED_NETWORKS=
```

Сервис подключается к турникетам напрямую, через обычный bridge-NAT Docker.

### macOS + Docker Desktop

Docker Desktop на macOS NAT-ит трафик контейнеров через основной интерфейс
(`en0`). Если турникет подключён отдельным кабелем/адаптером (например,
`10.3.198.0/24`) и принимает только адреса своей подсети, контейнер до него не
достучится. Решение — один общий релей на хосте.

В `.env`:

```env
TURNSTILE_RELAY_ENDPOINT=host.docker.internal:9000
TURNSTILE_RELAY_TOKEN=замените-на-секрет

RELAY_ALLOWED_NETWORKS=10.3.198.0/24
RELAY_ALLOWED_PORTS=80
```

Секрет можно сгенерировать командой `openssl rand -hex 16` и вставить в
`TURNSTILE_RELAY_TOKEN`.

`RELAY_ALLOWED_NETWORKS` — подсеть, в которой находятся турникеты. Узнать её
можно по адресу турникета и маске (`ifconfig`, `netstat -rn`). Несколько
подсетей перечисляются через запятую.

Запуск — сначала релей, потом сервис:

```bash
# терминал 1: релей на хосте
python3 scripts/relay.py

# терминал 2
docker compose up -d --build
```

Для фонового запуска релея:

```bash
nohup python3 scripts/relay.py > relay.log 2>&1 &
```

Релей читает тот же `.env`, слушает порт из `TURNSTILE_RELAY_ENDPOINT` и
маршрутизирует запросы по заголовку `X-Target-Host`. Для нескольких турникетов
ничего менять не нужно: достаточно, чтобы их подсети входили в
`RELAY_ALLOWED_NETWORKS`.

Важно:

- релей запускается **на хосте**, а не в контейнере — он должен находиться там,
  откуда доступны подсети турникетов;
- без `RELAY_ALLOWED_NETWORKS` релей не стартует (fail closed);
- токен должен совпадать у релея и сервиса — они читают один `.env`;
- релей не переживёт перезагрузку Mac сам по себе; для постоянной работы
  запустите его в терминале или оформите `launchd`-агент.

### Без Docker

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt

set -a
. ./.env
set +a

uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

Интерфейс: <http://localhost:8000>.

При нативном запуске на macOS релей не нужен — у процесса хоста есть прямой
доступ к подсетям. Если в `.env` остались relay-переменные, переопределите их
пустыми значениями:

```bash
TURNSTILE_RELAY_ENDPOINT= uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

## Эксплуатация

### Логи

```bash
docker compose logs -f --tail=100
```

Логи релея — в том терминале, где он запущен (или в файле, если запускали с
`nohup`).

### Состояние

```bash
curl -s http://localhost:8080/api/status | python3 -m json.tool
curl -s http://localhost:8080/api/devices | python3 -m json.tool
```

У каждой проходной видны `connected`, `last_error`, `last_sync_at`, количество
событий и проходов.

### Остановка и запуск

```bash
docker compose stop      # остановить
docker compose start     # запустить снова
docker compose down      # остановить и удалить контейнер
```

Данные лежат в `./data` и при `down` не удаляются.

### Обновление

```bash
docker compose up -d --build
```

База и настройки проходных сохраняются. `.env` при обновлении не перезаписывается.

### Где данные

```
data/turnstile.db       # SQLite
data/turnstile.db-wal   # журнал WAL
data/turnstile.db-shm   # разделяемая память WAL
```

Не удаляйте `-wal` и `-shm` на работающем сервисе: там могут быть ещё не
перенесённые в основную базу транзакции.

### Резервная копия

Согласованный снимок без остановки (файл `/data/backup.db` не должен
существовать заранее — `VACUUM INTO` создаёт его):

```bash
docker compose exec turnstile python -c \
  "import sqlite3; c=sqlite3.connect('/data/turnstile.db'); c.execute(\"VACUUM INTO '/data/backup.db'\"); c.close()"
```

Или остановить сервис и скопировать весь каталог `data/`.

### Сброс данных

```bash
docker compose down
rm -rf data
docker compose up -d
```

После этого первая проходная снова создастся из `.env`.

## Диагностика

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| `Cannot connect to the Docker daemon` | Docker Desktop не запущен | Запустите Docker Desktop и повторите команду |
| В шапке «Нет связи», `last_error: timed out` | Турникет выключен, неверный IP или нет маршрута | Проверьте `curl http://<ip>/` с хоста, кабель и подсеть |
| `connection refused` | Неверный порт или контейнер не доходит до устройства | Проверьте порт; на macOS используйте релей |
| `401 Unauthorized` от релея | Токен не совпадает | Сверьте `TURNSTILE_RELAY_TOKEN`; перезапустите релей после правки `.env` |
| `403 Forbidden` от релея | Цель вне `RELAY_ALLOWED_NETWORKS` или порт не разрешён | Добавьте подсеть/порт в `.env` и перезапустите релей |
| `502 Bad Gateway` от релея | Релей не может подключиться к турникету | Проверьте адрес и доступность с хоста |
| `address already in use` при старте релея | На порту уже висит старый релей | `lsof -tiTCP:9000 -sTCP:LISTEN` и завершите процесс |
| Порт 8080 занят | Другой сервис | Измените `ports` в `docker-compose.yml` |
| `database is locked` | Запущено несколько экземпляров сервиса | Оставьте один контейнер/один worker uvicorn |
| Связь есть, но событий нет | Нет новых событий нужной категории | Проверьте `EVENT_CATEGORIES=0` и журнал турникета |
| Таблица пустая после запуска | Не создана проходная или старая база | Проверьте `/api/devices`; `.env` создаёт устройство только на пустой базе |

## Настройки

| Переменная | По умолчанию | Описание |
|---|---|---|
| `TURNSTILE_HOST` | — | IP/имя для создания первой проходной на пустой базе |
| `TURNSTILE_NAME` | `Проходная 1` | Алиас первой проходной |
| `TURNSTILE_PORT` | `80` | Порт первой проходной |
| `TURNSTILE_PASSWORD` | пусто | Пароль веб-интерфейса первой проходной |
| `TURNSTILE_RELAY_ENDPOINT` | пусто | Адрес общего релея (`host:port`); включает маршрутизацию по заголовку |
| `TURNSTILE_RELAY_TOKEN` | пусто | Общий секрет релея (проверяется по `X-Relay-Token`) |
| `RELAY_ALLOWED_NETWORKS` | — | CIDR-подсети, куда релею разрешено подключаться (обязательно для релея) |
| `RELAY_ALLOWED_PORTS` | `80` | Разрешённые порты целей |
| `RELAY_LISTEN_HOST` | `0.0.0.0` | Адрес, на котором слушает релей |
| `RELAY_MAX_CONNECTIONS` | `64` | Лимит одновременных соединений релея |
| `TURNSTILE_PROXY_MAP` | пусто | Устаревшая альтернатива: статические пары `адрес=релей:порт` |
| `POLL_INTERVAL` | `2` | Период опроса журналов, секунды |
| `BACKFILL_DAYS` | `30` | Глубина импорта истории при первом запуске (`0` — всё) |
| `EVENT_CATEGORIES` | `0` | Категории событий: `0` — доступ по идентификатору, `1` — без идентификатора, `2` — состояния ОЗ, `3` — входы/выходы, `4` — функционирование, `5` — сервис |
| `DB_PATH` | `/data/turnstile.db` | Путь к файлу SQLite |
| `TZ` | — | Часовой пояс контейнера (в compose — `Europe/Moscow`) |

## API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/health` | Проверка живости |
| `GET` | `/api/status` | Общее состояние и список проходных со статусами |
| `GET` | `/api/devices` | Список проходных: связь, модель, версия, счётчики |
| `POST` | `/api/devices` | Добавить проходную (`name`, `host`, `port`, `password`) |
| `PATCH` | `/api/devices/{id}` | Изменить название/адрес/порт/пароль |
| `DELETE` | `/api/devices/{id}` | Удалить проходную вместе с её событиями |
| `GET` | `/api/events` | Лента: `limit`, `offset`, `device_id`, `q`, `direction`, `passes_only`, `since`, `until` |
| `GET` | `/api/codes` | Агрегированные коды: `limit`, `offset`, `device_id`, `q`, `passes_only` |
| `GET` | `/api/stats` | Статистика: `period=today\|all`, `device_id` |
| `POST` | `/api/sync` | Внеочередной опрос всех проходных (только чтение) |
| `GET` | `/api/stream` | SSE-поток новых событий |

Примеры:

```bash
curl 'http://localhost:8080/api/events?device_id=2&passes_only=true&limit=5'
curl 'http://localhost:8080/api/codes?limit=10'
```

## Структура

```
backend/
  app/
    main.py        # FastAPI: API, SSE, управление проходными, статика
    manager.py     # супервизор: один коллектор на каждую проходную
    collector.py   # фоновый поток опроса турникета
    perco.py       # клиент WebSocket-протокола PERCo (stdlib)
    store.py       # SQLite: устройства, события, коды, статистика
    static/        # index.html, app.js, styles.css
  requirements.txt
scripts/
  relay.py         # релей с маршрутизацией по X-Target-Host
Dockerfile
docker-compose.yml
.env.example
```

## Как это работает

Веб-интерфейс контроллера открывает WebSocket на `/tcp` и обменивается
JSON-документами, разделёнными `\n\n`. События отдаются по одному в кадре,
в обратном хронологическом порядке. Контроллер не поддерживает подписку на
события: их нужно запрашивать. Сервис повторяет этот протокол на чистом
Python (без внешних WebSocket-библиотек — встроенный lighttpd контроллера
отклоняет стандартный handshake некоторых библиотек), опрашивает журнал раз в
`POLL_INTERVAL` секунд и дедуплицирует события по паре `(device_id, id)`.

Задержка появления прохода: обычно **2–3 секунды** (цикл опроса + короткое
ожидание конца пачки событий). В браузер событие приходит сразу после записи в
SQLite через SSE.

## Примечания

- Сервис никогда не отправляет команды управления ИУ, сброса журнала или
  изменения настроек. Единственное не-`get` сообщение — авторизация
  (`set: auth`), и только если задан пароль контроллера.
- На каждую проходную держится ровно одно постоянное WebSocket-соединение;
  зрители дашборда подключаются к сервису через SSE и не создают нагрузку на
  контроллеры.
- Если проходная недоступна, её коллектор автоматически переподключается с
  экспоненциальной задержкой до 30 секунд, не влияя на остальные устройства.
- При удалении проходной удаляются и её события из локальной базы.
- Запускайте ровно один экземпляр сервиса и один worker uvicorn: иначе на
  каждый турникет появится несколько соединений.
- `.env` содержит пароли и токен — он исключён из git.
